# ADR 0012: Shipping policy and server calculation

Accepted for Phase 1A, 2026-10-09. [Implementation sequence](../development/CHECKOUT-ORDER-PAYMENT-PLAN.md).

One validated, versioned document in `settings`, keyed `shipping`, owns delivery policy. Its unique key prevents duplicate policies. Saves use a revision comparison and an Atlas transaction with a fresh active ADMIN profile/version check. The same transaction records full before/after policy snapshots in `auditLogs`; actor/updatedBy use the canonical auth ID. Snapshots contain policy values only, never addresses, tokens or credentials. The editor exposes the latest five snapshots; restoring revalidates a draft and saves a new revision. Older audit history remains available. No startup defaults, automatic index synchronization or settings cache are introduced.

Missing or invalid/future-schema settings fail closed with SHIPPING_CONFIGURATION_REQUIRED. Disabled delivery means unavailable, not free shipping. The editor may save an unreviewed tax configuration, including a null tax reference, but order-authoritative resolution cannot quote payable delivery without the required reviewed tax facts. No production approval is inferred from Admin Save.

Tax references use immutable `taxPolicies` records. Product rates alone do not prove applicability to shipping/COD. A separate administrator workflow records `deliveryReview: { reference, reviewedAt: Date, purposes: [SHIPPING and/or COD] }` only after explicit confirmation of an actual professional review. It requires a reference/date, runs with fresh ADMIN authority and revision-safe Atlas persistence, and audits the unchanged rate/mode plus prior/new review evidence. It is not part of ordinary Shipping Settings Save and does not guess a GST rate. The review attests to the exact immutable rate/mode/exemption facts; changing those facts requires a new key and review. Exempt policies require an exemption reason. Calculations re-read the referenced policy and its review.

The pure calculator reuses `calculateTax` and integer-paise helpers. Its merchandise input is discounted, GST-inclusive goods payable, excluding shipping/COD. Threshold comparison is inclusive; dropping one paisa below the threshold reinstates shipping. Zero standard delivery is valid when explicitly configured. Monetary inputs are bounded to 1,000,000,000 paise, safe integers only. Shipping waiver and COD fee are separate; automatic free delivery never waives COD fees. Tax components use aggregate GST for delivery estimates; invoice jurisdictional splitting belongs to the checkout tax contract.

Coverage is merchant policy, not a PIN directory or courier guarantee. State/UT abbreviations are the application's explicit allowlist; inputs are trimmed, uppercased, deduplicated and bounded. PIN prefixes are 1–6 digits, destination PINs six digits, both starting 1–9. ALL_INDIA has no stored restrictions. ALLOW_LIST allows any matching state OR prefix; BLOCK_LIST blocks any matching state OR prefix. Neither has precedence. An empty allowlist is invalid. COD is evaluated only after serviceability, then enabled flag and COD exclusions; it cannot widen delivery coverage.

Quote TTL is 600–900 seconds. Online payment deadline is 900–1800 seconds. Phase 2 must derive the provider checkout timeout from the remaining server deadline with a safety margin of at least 60 seconds, refuse an already-expired session, and retain late-capture recovery. This is a future implementation requirement, not a promise that closing a browser prevents capture. COD's 1–168-hour deadline is an operational alert: it never automatically releases reserved stock. Explicit shipment/cancellation governs that stock in Phase 2.

Admin preview is rate-limited and server-executed, works against the form's unsaved policy, and marks unreviewed tax results as estimates. No public endpoint trusts a browser merchandise amount. Future checkout calls the internal server-only resolver after pricing fresh catalog/cart facts; final acceptance must revalidate policy revision in its transaction. The calculator has no I/O. Current reads are fresh, bounded settings/tax lookups, independent of line count.

FREE_SHIPPING coupon waivers are deliberately not implemented here: their paise cap, pricing engine contract, coupon UI/preview, state registry and tests must land together in 1B. No orders, reservations, claims, payment attempts, courier API or new dependency is introduced.
